# 여행 계획 웹페이지 설계

## 목표와 승인된 범위
사용자가 diet처럼 웹페이지에서 여행 계획을 직접 입력하고, 비밀번호를 입력한 뒤 기존 계획을 조회·수정한다. 공개 코드 저장소 namyikim/travel_plan을 GitHub Pages로 배포한다. 원격 업로드는 사용자가 권한을 연결한 뒤 수행한다.

개인용으로 사용하며 초기 설정에서 사용자 이름·저장소 이름을 입력받지 않는다. 신규 연결의 데이터 저장소는 namyikim/travel-data로 고정한다. 기존 암호화 연결 파일은 호환성을 유지한다.

## 화면과 동작
- 첫 화면: 비밀번호 입력, 잠금 해제 상태 및 오류 안내. 해제 전에는 여행 제목과 일정도 표시하지 않는다.
- 여행 목록: 여행 생성·선택. 여행명, 목적지, 시작일·종료일, 동행 인원 입력.
- 여행 상세: 날짜별 일정 목록. 시간, 장소, 이동 정보, 숙소, 메모 및 참고 URL을 등록·수정·삭제한다.
- 관련 정보: 등록한 지도·예약·참고 링크를 표시한다. 장소 이름으로 지도 검색 링크를 제공한다. 뉴스나 관광 정보를 자동 수집하는 기능은 이번 범위에서 제외한다.
- 설정: 비공개 데이터 저장소 연결, 암호화 연결 파일 만들기, 비밀번호 변경, 잠그기 및 연결 해제. 비밀번호 변경 시 이전 연결 파일과 Git 기록의 암호문이 남는다는 점을 안내한다.
- 모바일과 PC에서 사용하는 반응형 한국어 화면. 저장 중·완료·실패 상태를 명시한다.

## 구조와 저장
빌드가 필요 없는 index.html, style.css, app.js와 테스트 가능한 core.js, 별도 crypto.js 및 sync.js로 구성한다. 외부 런타임 의존성은 사용하지 않는다.

공개 저장소에는 코드와 암호화한 connect.json만 둔다. 여행 기록은 별도 비공개 저장소의 travel-data.json에 저장한다. 이 저장소는 사용자가 직접 만들고, 해당 저장소에만 Contents 읽기·쓰기 권한이 있는 토큰을 설정한다. 업로드용 권한과 데이터용 토큰은 구분한다. 초기 설정이 없으면 여행 정보를 보여주는 대신 설정 안내를 제공한다. diet의 연결 파일이나 토큰을 복사하지 않는다.

connect.json에는 PBKDF2-SHA256 600,000회 및 AES-GCM으로 암호화한 저장소 연결 정보를 둔다. 비밀번호는 8자 이상이며 원문을 코드·URL·파일에 기록하지 않는다. 공개 암호문에 대한 오프라인 추측 공격 가능성 때문에 충분히 긴 비밀번호를 안내한다. 여행 데이터 파일도 같은 비밀번호에서 별도 salt로 도출한 키로 AES-GCM 암호화한다. 원격 데이터 파일에는 암호화 버전·salt·IV·암호문만 기록한다.

비밀번호를 페이지 접속 때마다 입력한다. 복호화 데이터와 토큰은 세션 메모리에서만 유지하며 localStorage 등에 평문으로 저장하지 않는다. 잠그기·새로고침 시 다시 비밀번호를 요구한다. 동일 브라우저에서 실행되는 악성 스크립트까지 방어하는 구조는 아니므로 CSP를 적용하고 입력 내용을 HTML로 실행하지 않는다.

## 동기화와 오류 처리
명시적인 저장 버튼으로 GitHub Contents API에 저장한다. 원격 SHA를 사용하여 충돌을 감지한다. 충돌 시 자동 덮어쓰지 않고 최신 내용을 다시 불러오거나 입력을 유지해 다시 검토하도록 안내한다. 오프라인·권한 부족·토큰 만료·복호화 실패는 구분하여 안내하며 실패한 입력은 현재 세션에서 유지한다. 저장 전후 잠금 동작에는 미저장 변경을 버리지 않도록 확인을 제공한다.

여행과 일정에 안정적인 ID를 부여한다. 시작일 이후의 종료일, 실제 달력 날짜, 여행 기간 안의 일정, 양의 동행 인원, 정상 시간 및 http/https URL을 검증한다. 기간을 변경해 기존 일정이 범위를 벗어나면 자동 삭제하지 않고 변경을 차단하여 먼저 수정하도록 안내한다.

## 배포와 확인
GitHub Pages main/root 배포 설정과 비공개 데이터 저장소 준비 절차를 README에 기록한다. 최초 배포 이후 예상 접속 주소는 https://namyikim.github.io/travel_plan/ 이며 배포 성공 전에는 접속 가능하다고 주장하지 않는다.

Node 기본 테스트로 데이터 검증, 일정 CRUD, 날짜 범위, 암호화 왕복 및 잘못된 비밀번호 거부, API 충돌·권한 오류를 확인한다. 가능한 브라우저 검증으로 잠금 전 정보 비노출, 입력·저장·재조회, 잠금 재진입과 모바일 레이아웃을 확인한다. 실제 데이터용 토큰 설정 전에는 모의 API로 검증하고 실제 동기화·배포 여부를 별도로 보고한다.
